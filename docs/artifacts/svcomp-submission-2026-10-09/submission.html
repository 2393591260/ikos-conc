Tool Submission

Since SV-COMP 2027, tool submissions consist of the following parts only:

  1. An archive with the tool published at Zenodo.
    The archive has to meet the following requirements.
    • The archive is publicly available and contains a LICENSE that allows reproduction and evaluation of the tool by anybody and does not place any restriction on the tool output (log files, witnesses).
    • The archive contains a README file that describes the contents.
    • The archive contains a script smoketest.sh that runs the tool on some simple example(s) that are also in the archive.
    • The tool is archived in a ZIP file (.zip), which contains exactly one directory (no tarbomb), with the files LICENSE, README, smoketest.sh, and all other files and folders of the tool.
    • The tool does not exceed an stdout/stderr limit of at most 2 MB.
    • The tool has an option to report its version (ideally --version).
    • The archive does not contain large amounts of unnecessary data, such as repository data (.svn, .git), source files, aux folders like __MACOSX, and test files.
    • The tool should not require any special software on the competition machines; all necessary libraries and external tools should be contained in the archive. Standard packages that are available as Ubuntu packages can be requested via an entry in the FM-Tools repository.
    • The tool should be executable from any path, and should not expect the working directory to match the tool directory.
  2. An entry at the FM-Tools repository named <tool_id>.yml.
    The structure of the file is described in schema.yml [we refer to the version after this merge request is merged]. In particular, the file has to contain
    • description that shortly explains the principles of the tool and the components it uses,
    • a version entry containing the DOI of the archive mentioned above,
    • a participation declaration for each competition track the tool wants to participate in, where each such a declaration includes
      • the tool version participating in the track,
      • a jury member who is (a) a contributing designer/developer of the submitted tool (witnessed by occurrence of the person’s name on the tool's project web page, a tool paper, or in the revision logs) or (b) authorized by the competition organizer (after the designers/developers of the tool were contacted about the participation),
      • label meta_tool if the tool is a meta-verifier,
      • label ai if the tool uses an LLM or other sophisticated kind of artificial intelligence, and
      • the list of categories the tool wants to participate in (with each declared category, the tool automatically participates in all its subcategories; it is possible to specify subcategories for which the tool's results will not be displayed).
    Note that the merge request will be merged only if the script smoketest.sh mentioned above successfully passes (exit code 0). Further, note that each tool participating in the previous year (except the inactive tools for which the community explicitly agreed to not evaluate them again) will be automatically registered for the current competition as inactive. If you want to actively participate with this tool, please add a jury member and delete the inactive label.

    Please do not create/modify your <tool_id>.yml file before this merge request is merged.

  3. A tool-info module for BenchExec added to the BenchExec repository. The tool-info module enables BenchExec to abstract from the concrete command-line interface by assembling the command line, parsing the output to determine the result/status, and to get tool version.
  4. Additionally, new jury members have to announce their e-mail address to the organizers.

In contrast to previous years, it is no longer needed to make any merge requests to category-structure.yml. It may be a good idea to look at <tool_id>.yml of some established tool for inspiration, e.g., at cpachecker.yml.

We strongly recommend to subscribe to the mailing list and the Zulip stream.

Qualification

To be qualified for the competition, each tool needs to have:

  • <tool_id>.yml merged in the FM-Tools repository with a non-trivial smoketest.sh, reasonable description, and correct labels,
  • a license in the archive with the tool satisfying the requirements given above,
  • conceptual or implementation differences compared to other participating tools,
  • a jury member who contributes to the development of the tool or has an approval from the organizers.

Submission of Competition-Contribution Papers

The requirements on competition-contribution papers will be specified later. In contrast to the previous years, we expect slightly less restrictions on the paper structure in order to reduce repetitive parts in the papers about new versions of established tools and to accommodate papers about interesting new benchmark categories etc.

If you did not find what you are looking for, please do not hesitate to contact Dirk Beyer (competition webmaster).
