## 一、提交物总览（自 SV-COMP 2026 起的新流程）

自 2026 年起，工具提交**只包含以下 5 个部分**：

### 1. 发布在 Zenodo 上的工具归档（archive）

归档必须满足：

- **公开可访问**；包含 **LICENSE**，该许可证须允许**任何人复现和评估该工具**，且**不得对工具输出（日志文件、见证文件）施加任何限制**。
- 包含 **README** 文件，描述归档内容。
- 包含脚本 **smoketest.sh**，在归档内自带的简单示例上运行工具。
- 工具以 **ZIP（.zip）** 归档：**恰好包含一个顶层目录**（不得是 tarbomb），内含 LICENSE、README、smoketest.sh 以及工具的所有其他文件和文件夹。
- 工具的 **stdout/stderr 输出上限为 2 MB**。
- 工具须有报告自身版本的选项（理想为 `--version`）。
- 归档**不得包含大量不必要的数据**：如版本库数据（`.svn`、`.git`）、源文件、`__MACOSX` 之类辅助文件夹、测试文件。
- 工具**不应要求竞赛机器上装有任何特殊软件**；所有必需的库和外部工具都应包含在归档内。以 Ubuntu 包形式提供的标准包，可通过在 **FM-Tools 仓库**中登记来申请。
- 工具应能从**任意路径**执行，且不应假定工作目录就是工具所在目录。

> **讲解（对清单 A/B 的硬性复核）：**
> - **清单 A1–A10 每一条都在本页得到官方原文确认**，包括"恰好一个顶层目录""输出 ≤ 2MB""无 .git/源码/`__MACOSX`/测试文件""任意路径可执行""不依赖工作目录"。
> - **G5 得到证实：归档必须"公开可访问（publicly available）"**。注意原文约束的对象是 **Zenodo 归档**；工具代码仓库是否必须 public，本页未直接写，但第 6 节论文要求提供项目仓库 URL，且许可证须允许任何人复现——**仓库与 Zenodo 都应保持公开**，`github.com/2393591260/ikos-conc` 保持 public 即可。
> - 许可证有一个易漏的附加条件：**不得限制工具输出（日志、见证）的使用**。NASA-1.3 本身不限制输出，符合，但需确认归档 LICENSE 文本没有额外附加条款。
> - Ubuntu 标准包可以不打包、改在 FM-Tools 里申请（对应 B7 / G2）；但 APRON、LLVM14 这类非标准包必须自包含。

### 2. FM-Tools 仓库中的条目：`<tool_id>.yml`

文件结构在仓库中有说明，必须包含：

- **version 条目**：内容为上述归档的 **DOI**；
- **参赛声明（participation declaration）**；
- 一名 **jury member（评审/陪审团成员）**，须满足 (a) 是所提交工具的**贡献设计者/开发者**（以其名字出现在工具项目网页、工具论文或版本修订记录中为证），或 (b) 经竞赛组织者授权（前提是组织者已就参赛联系过该工具的设计者/开发者）；
- 若工具是**元验证器（meta-verifier）**，加标签 **meta_tool**；
- 若工具使用 **LLM 或其他高级人工智能**，加标签 **ai**；
- **描述**：简要说明工具的原理及其使用的组件。

**注意：**

- **上述 smoketest.sh 只有成功通过（exit code 0），合并请求（MR）才会被合并。**
- 上一年度参赛的每个工具会被自动注册为 **inactive（不活跃）** 状态；若想以该工具**主动**参赛，需添加一名 jury member 并删除 **inactive** 标签。（新工具首次参赛无此问题。）

> **讲解（对应清单 B/E）：**
> - **B2 再次确认：version 字段填的不是版本号字符串，而是 Zenodo DOI。**
> - **B4/E4 的 jury member 是合格性硬条件**，且身份证据有明确三种载体：项目网页、工具论文、修订日志。我们的 jury member 名字必须出现在这三处之一——首次参赛最方便的做法是**确保其名字出现在 GitHub 项目页（README 作者列表）和提交记录中**。
> - **B5 确认：不用 LLM 就不标 ai，不是元验证器就不标 meta_tool。**
> - smoketest 是 MR 合并的门禁——CI 会实际运行它，A4 必须真的 exit 0，不能只是本地声称。

### 3. BenchExec 的 tool-info 模块（加入 BenchExec 仓库）

tool-info 模块使 BenchExec 能屏蔽具体命令行接口的差异：负责**拼接命令行、解析输出以确定结果/状态、获取工具版本**。

> **讲解（对应清单 C）：** 即 `benchexec/tools/ikos-conc.py` 的 `cmdline()`、`determine_result()`、`version()` 三项职责，本页原文确认。

### 4. 向 category-structure.yml 提交合并请求（MR）

声明工具想参加哪些类别。

- 工具基本上是**对每个元类别**（如 `C.ReachSafety`、`C.Overall`）**声明参加与否**。
- **opt-out（退出）**：工具想参加某个元类别，但希望**隐藏**其在该元类别所含某些基础类别上的结果。例：工具参加 `C.ReachSafety` 但不能正确处理浮点数，可对 `C.unreach-call.Floats` 提出 opt-out。效果是：**它仍会在包括 Floats 在内的所有基础类别上被评测**（结果仍计入 `C.ReachSafety` 的得分），但在官网结果表中 `C.unreach-call.Floats` 的分数被替换为破折号、不报告该基础类别的执行结果。
- **opt-in（加入）**：工具想参加某些**基础类别**，但**不想参加**包含它们的元类别。例：可以只 opt-in `C.unreach-call.ControlFlow` 和 `C.unreach-call.Loops`，而不参加 `C.ReachSafety`。

> **讲解（对应清单 D，比规则页更清楚）：**
> - **opt-out：参加元类别、照样跑任务、分数照算进元类别，但子类别列上显示为破折号。**——它**不能用来避免罚分**！跑出来的 −16 仍然计入元类别，只是对外不可见。
> - **opt-in：只参加指定基础类别，不参加其元类别**——这才是"我们只想跑 no-data-race、不想在 C.Overall 等元类别被汇总"的正确机制。
> - 对我们的启示：若目标**仅限 `C.no-data-race.Concurrency`**，应使用 **opt-in** 进入该基础类别、不参加更大的元类别；若已参加并发元类别，则对处理不了的子类别 opt-out 只影响"展示"，不影响实际计分。**D2 清单里"默认全参加"的标注需要按此重新决策。**

### 5. 新 jury member 须向组织者告知邮箱地址

新加入的 jury member 必须把**电子邮箱**告知组织者。

> **讲解：** 这是清单里没有的一项动作——确定 jury member 后，需按组委会渠道（邮件/Zulip）报备邮箱。

## 二、流程性变化（与往年不同）

- **不再需要通过 EasyChair 进行论文投稿/注册**即可参赛。
- 短文（称为 **competition contributions，竞赛贡献论文**）有**独立且可选的**提交截止期，安排在**竞赛结果公开之后**（对应清单 F 的 2026-12-17）。
- 强烈建议订阅竞赛**邮件列表（mailing list）**和 **Zulip 频道**。

> **讲解：** 参赛本身只需"归档 + FM-Tools + tool-info + category MR"四个技术动作；短文是可选的赛后动作，不影响参赛资格。

## 三、Qualification（合格条件）

工具要获得竞赛资格，必须具备：

1. FM-Tools 仓库 `<tool_id>.yml` 中 **flags 正确**；
2. 工具归档中含满足上述要求的**许可证**；
3. 与其他参赛工具相比存在**概念或实现上的差异**；
4. 一名对工具开发有贡献的 **jury member**，或持有组织者的批准。

> **讲解（对应清单 E1–E4）：** 四条与清单 E 完全一致，本页为官方原文，无新增条件。

## 四、Requirements for Competition Contribution Papers（竞赛贡献论文要求）

论文结构**为推荐而非强制**，但下列信息必须提供：

### 标题、作者与摘要
- 常规 LNCS 格式。建议标题中包含工具名和/或技术名。
- **在论文中标注 jury member**（名字后加星号并加脚注说明）。

### 1. 验证/确认方法（Verification/Validation Approach）
- 简述工具所依据的理论；描述所用的**抽象域（abstract domains）和算法**；引用阐述技术细节的概念论文。

### 2. 软件架构
- 所用库与外部工具（如解析前端、SAT 求解器）；
- 软件结构与架构（如参赛使用的组件）；
- 实现技术（如编程语言）。

### 3. 方法优缺点讨论
- 对各基准类别结果的评估：何处成功、何处失败、原因。

### 4. 工具设置与配置
- **下载说明**（可下载工具的公开网页），须引用工具的**精确版本**（不得引用"最新版本"等不稳定、不可复现的说法）；
- 安装说明；
- **参赛声明**（明确声明参加哪些类别）；
- **配置定义**：整个基准集所有类别只有一套全局参数，必须给出参数集的完整定义；详见规则页 Parameters 部分。

### 5. 软件项目与贡献者
- 联系信息（项目网页、参与人员）；
- 软件项目信息、许可证、开发模式、托管机构、贡献者致谢。

### 6. 数据可用性声明（Data-Availability Statement）
- 发布工具归档并在此处通过 **DOI** 引用以保证可复现性；同时提供项目网站和代码仓库的 URL。

### 参考文献
- 关于工具所用方法的深入论文的书目引用。

> **讲解（对我们的启示）：**
> - 短文虽在赛后（2026-12-17）提交，但**第 4 节要求的"全局参数集完整定义"和"参赛类别声明"在赛前 MR 阶段就必须定型**，赛后只是照抄。
> - 第 1 节要求写清抽象域与算法：对我们即 thread-modular 抽象、lockset、happens-before，并引用 IKOS/APRON 的概念论文。
> - 第 6 节要求 DOI + 仓库 URL，再次印证 G5：仓库需要公开且稳定。

## 五、对核验清单的复核结论

| 清单项 | 提交页复核结论 |
|---|---|
| A1–A10 | **全部得到原文确认**（单一目录、LICENSE、README、smoketest、2MB、--version、无 .git/源码/`__MACOSX`/测试、任意路径可执行、不依赖工作目录） |
| A2 LICENSE | 加强：须允许任何人复现/评估，且**不得限制日志与见证输出的使用**——NASA-1.3 符合，核对无附加条款即可 |
| A5 自包含 | 确认：特殊库（APRON/LLVM14）必须打包；Ubuntu 标准包可在 FM-Tools 申请（B7） |
| B2 version = DOI | **原文再次确认** |
| B4 / E4 jury member | **合格硬条件**；身份证据限三种载体（项目网页 / 工具论文 / 修订日志）；新成员**还须向组织者报备邮箱**（清单遗漏，已补入下方行动项） |
| B5 标签 | 确认：不用 LLM、非元验证器则两个标签都不加 |
| C 模块 | 三项职责（拼命令行、解析结果、取版本）原文确认 |
| D1 category MR | 确认：按元类别声明参加与否 |
| **D2 opt-out/opt-in** | **需修正认识**：opt-out 仍会跑任务、分数照算进元类别，仅展示为破折号，**不能用来规避罚分**；只想跑 no-data-race 基础类别应使用 **opt-in 且不参加元类别** |
| E1–E4 | 与提交页 Qualification 四条完全一致 |
| **G5 公开可访问** | **证实**：Zenodo 归档必须 publicly available；论文要求提供公开仓库 URL；仓库应保持 public |
| G2 Ubuntu 包清单 | 机制确认：标准包走 FM-Tools 登记，仍需在干净容器验证 smoketest |

**新增/修订的行动项：**
1. **D2 重新决策**：明确我们到底参加哪些元类别；若仅跑 `C.no-data-race.Concurrency`，用 opt-in（不参加并发元类别/C.Overall），而不是靠 opt-out。
2. **jury member 邮箱报备**：确定人选后，通过邮件/Zulip 向组织者告知邮箱（原清单漏项）。
3. **jury member 身份留痕**：确保其名字出现在 GitHub 项目页（README 作者）+ 提交记录中，作为"贡献开发者"证据。
4. **LICENSE 附加核对**：确认无限制工具输出（日志、见证）的条款。
5. 无需 EasyChair 注册；短文为赛后可选（2026-12-17）。

**总体判定：** 提交页与规则页口径一致，清单 A/B/C/E 的设计全部符合官方要求，**G5 已由本页排除**；当前仍待办的核心是：D2 按 opt-in/opt-out 正确语义重新配置、DOI 与 jury member（含邮箱）补齐、G2 容器验证、G3 data_model、G4 见证验证器实测。
