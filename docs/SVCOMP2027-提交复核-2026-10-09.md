## 2. FM-Tools 条目

YML 通过本次获取的 main schema 与 `add-categories` 待合并 schema 的 JSON Schema 校验。工具 ID、C 输入、DOI、版本引用、Verification track、jury/participants、技术/组件字段齐全。`track: Verification` 正确，不能改为 `no-data-race`。

**缺少实际参赛类别 `categories`。** 当前两个 schema 都未把它列为 required，因此“schema 通过”不能证明满足新 submission 页面。官方要求每个 participation 声明类别，并说明“不再需要 category-structure MR”。只参加数据竞争基础类别时，迁移准备内容为：

```yaml
competition_participations:
  - competition: "SV-COMP 2027"
    track: "Verification"
    tool_version: "svcomp27"
    categories:
      - C.no-data-race.Concurrency
    # 保留现有 jury_member 和 participants
```

不要列 `C.Concurrency`/`C.Overall` 这类覆盖其他属性的元类别。`suppressed_categories` 只隐藏显示，不减少执行任务或元类别计分。

**迁移时机受官方明确限制。** submission 页面写道：

> Please do not create/modify your `<tool_id>.yml` file before this merge request is merged.

其中链接指向 !1112，而它本次实查尚未合并。先准备类别声明，待 !1112 合并或组织者明确给出迁移安排后更新远端条目；不能单方面按草案改完就宣称合规。已有 category-structure MR 不是当前页面要求的额外必需提交。

描述需要收敛：当前“sound in both directions: FN=0 and FP=0”是没有完整证明支撑的保证。建议描述两层方法、所用组件和 unsupported→UNKNOWN 行为，不把有限回归零误判写成算法保证。LLM 辅助开发不等同于验证器运行时使用 LLM；当前检查的分析链路无 LLM 调用，因此没有仅因开发工具而新增 `ai` 标签的依据。

## 3. BenchExec adapter

版本解析得到 `3.5`；ILP32/LP64 明确透传；非零退出/超时及未知结果处理保守。在项目外临时工作目录，当前 adapter 两架构的 smoke 都 exit 0、返回 false、输出 1308 字节并生成 2.2 witness。

但有两个可复现的集成缺口：

1. **归档根目录无法定位 executable。** `find_executable("ikos")` 只查 root，实际文件在 root/bin。BenchExec `ToolLocator(tool_directory=install, use_path=False, use_current=False)` 失败；指定 install/bin 才成功。建议用 `find_executable("ikos", subdir="bin")` 并按归档根目录验证。
2. **依赖文件清单不完整。** 默认 `program_files()` 实际只返回 `install/bin/ikos`，缺少 wrapper、analyzer、frontend、LLVM/APRON 和头文件。文件搬运/分布式运行依赖该清单时会失败。可用相对 executable 目录的 `REQUIRED_PATHS = [".."]` 覆盖归档；本地原地运行成功不验证文件搬运。

进一步建议：拒绝非 no-data-race 属性及非 C 任务，避免固定 race 分析返回被误用于别的属性；缺少/不支持的数据模型不猜为 ILP32。“2026 集全 ILP32”不是 2027 的保证。当前 `options=[]` 可工作，但 wrapper 不接受任意 IKOS 原生命令行选项，需要在将来添加选项时核对。

工具版本 `svcomp27` 作为条目键与 `--version` 输出 `3.5` 不同，不构成已发现的 schema 错误；建议新发布版本带 ConC revision，并让 witness producer.version 一致，便于复现。

## 4. Zenodo 实物与包装

[DOI 10.5281/zenodo.23122650](https://zenodo.org/records/23122650)公开可访问，文件 `ikos-conc.zip` 95,356,370 字节。其公布 MD5 与本地 ZIP 一致：`232bc0f5ab3d0b710c2752e3d858c428`，因此可直接审查本地同一实物。

归档含 699 个文件，只有 `ikos-conc/` 一个顶层目录，有 LICENSE.txt、README.md、可执行 smoketest.sh 和内置示例，没有本次检查的 .git/__MACOSX/__pycache__/pyc/db/cpp 残留。
**同一上传 ZIP 已在全新 Ubuntu 24.04 容器通过 smoketest，exit 0**：只安装声明的 Ubuntu packages 及解压用 unzip，再解压并运行。
另外，现有包装镜像中断网、不同 cwd 的 smoketest exit 0；该旧镜像 binary 与上传 ZIP 不同，不能把它的结果混作同一实物验证。

**上传归档不是当前修复版。** analyzer SHA256：

- 上传版：`e5ff447c639eb42ef098f2ec3cda15e11d50361c02e35aa7c7aeb9de82fc9026`
- 当前版：`3043999b0e36620f977aeb8d397afeb3921bc4d445d78df5945eb80ccbd8424c`

witness wrapper 也不同。必须以当前选定版本重新打包，进行包装后的测试，再发布新 Zenodo 版本并更新条目 DOI。不能按旧清单所写“同 DOI 更新版本”理解：正常创建新 Zenodo 版本会得到新版本 DOI，concept DOI 才跨版本保持。本次记录 concept DOI 为 `10.5281/zenodo.23122649`。

**实物仍含三个已修复的正确性缺陷。** 对同一上传 ZIP 解压后运行历史 P0 runner，ILP32/LP64 都得到：

| 用例 | 上传版 BMC 输出 | 已核实含义 |
|---|---|---|
| `exclusive-flag.c` | definitely UNSAFE | FP：无真实竞争却被确认 |
| `overlapping-widths.c` | SAFE | FN：忽略重叠访问宽度 |
| `published-before-init.c` | SAFE | FN：未证未发布的 private_init 过滤 |

这直接说明当前 DOI 对应的发布版不能作为正确性修复后的版本；smoketest 成功仅证明能执行。
命令为 `python3 -B docs/review-repros/bmc-2026-10-08/run.py --ikos <解压目录>/ikos-conc/bin/ikos --bits 32`（再以 64 重复），20 条原始观察随本轮证据保存。

NASA-1.3 允许使用/分发/复现，本轮未发现对日志或见证输出的限制；不要只凭 SPDX 字段认为所有包装义务已经核实。归档 README 应给出对应源码版本/获取地址及修改说明，并核对所打包第三方组件的 license/notice。官方正文使用 LICENSE/README 名称，本归档用 LICENSE.txt/README.md；是否被 CI 脚本接受须以实际 CI 为准，未断言仅扩展名就违规。

smoketest 当前覆盖直接分析及 demote+BMC，但最后的 shell pipeline 只检查 grep 成功，且没有验证正式 wrapper、witness、安全对照。建议它覆盖正式入口的 race 和 safe 示例，检查真实退出码与见证，而非只找到一个 unsafe 字符串。stdout/stderr 的 2 MB 限制仍须在提交配置和代表性异常任务下验证；1308 字节的 smoke 不构成全量保证。

## 5. 2027 witness 与其他操作

官方 2027 表格明确：**C.no-data-race 所有基础类别，violation witness 为 2.2 或更高；correctness witness 不支持、也不要求。** 规则要求支持格式的结果附带 `witness.yml`。因此当前选择 YAML 2.2 方向正确，不应照搬 2026 的 GraphML 限制，也无需为数据竞争 TRUE 专门新增 correctness witness。

格式版本正确不代表独立验证成功。本轮只验证 smoke 生成文件/版本；选中执行与源码坐标、线程身份、`.i` 的原 `.c` 映射及正式 validator 验收仍需完成。此前旧清单声称“CPAchecker 已确认”，没有本轮证据支撑，不沿用。

新 jury member 还需向组织者告知邮箱。公开 git revision logs 中有 Ronghui Ruan，支持其开发贡献身份；旧清单记载邮箱已报备，但本轮未读取私人邮件，需以用户已收到的回复确认，已完成则不必重复。订阅官方邮件列表、加入 Zulip 属强烈建议。competition-contribution paper 的要求官方尚待另行说明，不把旧文档的“可选”作为确定结论。

建议优先替换仍含 FP/FN 的上传实物；准备工作顺序为：修复 adapter 定位/依赖清单 → 当前版本包装及正式入口 smoke/P0/独立 witness 验证 → 新 Zenodo 版本和 DOI → 按上游迁移时机补类别及修正描述 → FM CI 全绿与两个提交合并。若 runner 阻塞，先取得当前 job 原因，再通过现有赛事沟通渠道解决；本轮没有发送外部消息或修改远端提交。
