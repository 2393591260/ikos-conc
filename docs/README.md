## 比赛与论文的整体路线

**2026-10-11 规划：比赛交付优先，机制优化与论文证据同步积累。**
目标是让 AI 保守证明更多 SAFE，让按需 BMC 确认更多真实竞争，同时控制端到端成本；
不预设 TP/TN 上限，不把清空 UNKNOWN 或全面超过 Goblint/Dartagnan 作为结束条件。
当前计数与证据范围只见[本页基线](#current)。

用户暂未确定汇报日期或研究论文投稿场所。从 M0 起就维护可汇报的提纲与论点表，
不用等研究全部完成。比赛贡献短文和完整研究论文有不同出口，不能把前者的截止套给后者。

### 每轮实施都走同一条证据流程

1. 从当前台账选具体任务，核对 YAML、输入、数据模型和版本。SAFE 参考优先 Goblint；
   RACE 参考优先 Dartagnan。历史结果先复核，参考 UNKNOWN/失败不冒充能力上限。
2. 读程序与相关 IKOS 代码，预测关键共享读、锁、创建/join、地址与值流的状态。
   在固定参考配置上观察对应机制，再用最少探针定位 IKOS 第一次丢失信息的位置。
3. 从具体文件提炼通用规则，列出前提、近似方向、保持性依据、前提失效时的回退；
   不按文件名、标签或基准形状加例外。无法迁移的规则记录原因，继续下一入口。
4. 先准备最小正例、对照和适用变体，再在拥有该语义的层实现。
   前端改动独立 A/B；保护摘要不能把无序写队列当顺序执行取“最后一次写”。
5. 构建并同步实际执行的 install，做相关双架构/P0 回归，跑同配置 AI 与 AI+BMC 全量逐项配对；
   新增/变化 FALSE 检查所选执行及对应 witness。发现漏报或假执行先修正确性。
6. 判定收益和成本分别分析。通过后立即提交单机制 commit，写明前后配对数字，
   更新所属手册和小型证据；零收益/不支持也进入现有台账，不另开快照文档。

一个优化节点结束，表示该批入口已实现并验收，或已有具体的失败证据、缺失前提和后续条件；
不表示整个工具再无可提高之处。要新增大型算法或外部支持时提出下一节点，
不能用“还剩 UNKNOWN”无限延长已定义的阶段。

### 发布与研究如何并行

保留一个验收过的当前版本候选包；研究分支/构建、install 和验收实物分开，
避免后续构建覆盖已验收二进制。M2/M3 只有完整验收的提交可进入发布版本。
10/18 和 11/15 内部冻结后停止向该包加入精度扩展，只处理经验证的正确性或交付阻断修复。
官方 runner 或 validator 未就绪时，记录负责人、状态与待验收项，继续独立的本地工作；
不以本地模拟替代官方结果。全量扫描错峰执行，避免资源竞争污染比较。
