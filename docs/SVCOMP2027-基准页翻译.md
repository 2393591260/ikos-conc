## Benchmarks（基准）

本页描述用作竞赛基准的验证任务和核验任务，以及它们如何组织为类别。基础术语的定义见竞赛规则页。

### 一、验证任务（Verification tasks）

竞赛使用选自 **SV-Benchmarks 仓库**的验证任务。该仓库有若干对应不同编程语言的目录；语言目录内包含来自各种来源、以给定语言编写的程序的子目录。

**每个程序都配有一个任务定义格式（task-definition format）的 YAML 文件**。该任务定义文件描述：
- 与该程序相关的验证任务（和/或其他任务）；
- 以及用于无歧义解释该程序的其他信息（例如所采用的**数据模型** data model）。

对于每个验证任务，该文件规定了：**要检查的属性和期望结果（该期望结果在 SV-COMP 中不提供给验证器）**。

语言目录还包含：

- **properties 目录**：存放各属性的定义；
- **CONVENTION.md 文件**：解释基准仓库中使用的所有约定（如获取非确定性输入的特定函数、对执行环境的假设等）；
- **`*.set` 形式的任务集（task-set）文件**：列出 glob 模式，规定一组任务定义文件。

**基础类别（base categories）**由 bench-defs 仓库中的 `category-structure.yml` 定义。对每个基础类别，该文件规定了纳入（也可能规定排除）该类别的任务集文件。

- **每个基础类别的名称形如 `<语言>.<属性>.<后缀>`**，表明所考虑的编程语言和属性。
- 基础类别包含：被任何纳入（且未被任何排除）的任务集文件所代表的全部验证任务，且这些验证任务的属性与类别名称中的属性一致。

基础类别会被汇总为**一到两个层级的元类别（meta categories）**，同样由 `category-structure.yml` 定义。每个元类别的名称也以所考虑语言的名称开头。

> **讲解：**
> - 这段文字明确了三级关系：**程序 → 任务定义文件（.yml）→ 类别**。
> - 期望结果（答案）藏在任务定义 YAML 中，**工具看不到**；工具能拿到的是源码和 .prp 规约。
> - 类别名 = 语言 + 属性 + 后缀，与之前解答一致；"参加类别 = 该类别全部任务都跑"。

### 二、核验任务（Validation tasks）

核验任务有两个来源：

1. **人工构造的核验任务（crafted validation tasks）**，来自 SV-Benchmarks 仓库；
2. **由"一个验证任务 + 验证工具在竞赛中产出的见证"组合而成的核验任务。**

**第一类来源**的核验任务由任务定义文件描述，并按上述方式归入任务集文件和基础类别；这些基础类别汇总为元类别 **C.ValidationCrafted**。

**第二类来源**的核验任务，归入与其对应验证任务相同的基础类别和元类别。

- 此外，元类别 **C.Overall** 也包含 C.ValidationCrafted。
- 对于核验器的评估，目前只使用 C 语言的见证。
- **不纳入**第二类来源核验任务的情形：
  - 对应类别对相应种类的见证没有任何受支持的格式；
  - 或该格式仅在演示模式（demo mode）下受支持。

核验赛道的类别结构实际上有**两份副本**：一份只含正确性见证，另一份只含违例见证。

部分类别为**演示类别（demo categories）**。

> **讲解：**
> - 核验任务 = 给见证核验器（validator）做的"考题"：一部分是人工准备好的、已知好坏的见证（C.ValidationCrafted）；一部分直接取自竞赛中验证器产出的见证。
> - "只支持的格式才跑、demo 模式不跑"——与规则页见证表的口径一致：没有对应格式支持的类别，其见证不会被送入核验赛道。
> - 正确性见证、违例见证分别核验，因此有两份结构。

## 小结（结合前面文档）

1. **任务组织链**：SV-Benchmarks 仓库 → 每个程序配 `.yml` 任务定义（含属性、期望结果、数据模型）→ `.set` 任务集文件 → `category-structure.yml` 定义基础类别与元类别。
2. **两条赛道**：验证赛道（工具直接分析程序，产出 TRUE/FALSE + 见证）；核验赛道（核验器对见证做复核，任务分人工构造和现场生成两类）。
3. **当前状态**：2027 类别最终清单尚未生成，**准确的类别名、任务数、数据模型（ILP32/LP64）以 2026-11-03 任务冻结时的仓库为准**。
